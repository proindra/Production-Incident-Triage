1. Context
An on-call engineer gets paged at three in the morning. The alert reports a symptom, not a cause. Disk filling.
Replication lagging. Latency spiking. Error rate climbing.
The engineer has to do four things quickly and under pressure. Work out what class of problem this is. Find the
runbook that applies. Decide the severity. Know whether to escalate or handle it alone.
These decisions are made under time pressure and are affected by fatigue. Mature engineering organisations
build tooling to support them, and they are closely connected to the reliability engineering practices taught in Unit
2.
2. What to Build
A multi-agent service that accepts an alert payload with an on-call note, validates it, retrieves the operational
guidance that applies, proposes a cause class and severity, and routes the incident.
This is a production service, not a notebook.
The system never executes a remediation. It proposes a cause class and steps with supporting evidence. The
on-call engineer decides.
3. Corpus
PostgreSQL publishes its complete documentation for every supported major version. Select one major version.
All documents below are free to download.
 The PostgreSQL documentation for one major version, in particular the chapters on monitoring, write-ahead
logging and replication
 Three runbooks you write yourself for common PostgreSQL failures, in a consistent format
 A short severity and escalation policy you define
Prefer documents with a text layer. A scanned document needs optical character recognition (OCR) before it can
be indexed.
Why this corpus is difficult. The retrieval direction is inverted. Documentation is organised by cause: it
explains what each subsystem does and how to configure it. Alerts arrive as symptoms. Nothing in the
documentation is indexed by the words an engineer types during an incident.

4.1 The difficult case
The system will be tested against this scenario at the demonstration.
"Disk usage on the primary is climbing steadily. Table and index sizes are not growing. On-call note: disk
filling, cause unknown."
A search on disk usage retrieves the documentation on storage and table maintenance, which does not explain
this. A common cause of the pattern is a replication slot whose consumer has stopped: the server keeps
write-ahead log for the slot even when nothing is connected to it. That behaviour is documented in the replication
chapter, which nothing in the alert mentions. The system must reach this cause, cite the documentation, and give
a response appropriate to the selected major version.
At Evaluation 1, show the passages in your corpus that this case depends on, and the values you will test with.
Once confirmed, this is the reference answer for your demonstration.
5. Design Approach
The straightforward implementation embeds the request, retrieves the highest-scoring passages, and asks the
model to answer from them. This handles ordinary cases but not the case in section 4.1.
The reason is structural. A single retrieval pass returns passages resembling the question asked. The case in
section 4.1 turns on a provision the request never mentions, so a single embedding-based search is unlikely to
return it.
The required approach is an agent that:
1. Retrieves the provision that appears to apply
2. Determines whether any other provision modifies it, and searches for such provisions
3. Searches again, using a query derived from what it has read
4. Verifies that the retrieved passages support the answer
5. Retries with a different strategy, or escalates, if they do not
Steps 2 and 4 distinguish an agent from a fixed pipeline. Both are assessed.

Requirement
A3
Verify every answer against the passages retrieved, before returning it. Every citation must resolve to
retrieved text. If verification fails, search again with a different strategy or escalate. An unverified answer must not
be returned. This is the basis of F7.
A4
Expose the service with FastAPI. Runs take tens of seconds, so execute them asynchronously: return a run
identifier immediately, and the caller polls a status endpoint or receives a callback. Justify the choice. Place a
queue or task runner between submission and execution.
A5
Timeouts on every model and tool call, bounded retry with exponential backoff, a circuit breaker on the
provider, and graceful degradation along a defined fallback path. All must be demonstrable on request. A run
that did not complete must not be returned as a confident answer.
A6
Track per agent and display on the dashboard: task success rate, steps and tool calls per run, latency end to
end and per step, retry rate, container uptime.
A7
docker compose up --scale <agent-worker>=3 must work. Measure the effect on throughput and p95,
using the stub described in D6. If scaling does not help, identify the actual bottleneck.
A8
A simple web client that submits a request, obtains the result, and displays the recommendation with citations
and the escalation path. No marks for appearance.
7. LLMOps Requirements
Unit 3 — retrieval, prompt management, evaluation, guardrails, monitoring.
#
Requirement
L1
Orchestrate retrieval with LangChain or LlamaIndex; index with FAISS or Chroma. Document the chunking and
embedding strategy and how it addresses the difficulty in section 3. Re-embedding must be possible without
rebuilding the whole index.
L2
Treat prompts as versioned artifacts, and record the prompt version with every response. Compare at least two
prompt variants on the same evaluation set; report which performed better, on which metric, and by how much.
L3
Build a fixed evaluation set of at least 20 scenarios, each with its expected outcome and the passage that
supports it, including the case in section 4.1, runnable as a batch from the command line. Use TruLens or
equivalent. Report groundedness, context relevance, faithfulness and hallucination rate, stating how each is
computed. Then make one deliberate change and report all four metrics before and after.
L4
Prompt injection defence on every free-text field reaching a model, output filtering so the system cannot issue
a determination it is not authorised to make, and toxicity detection on input and output. Agents are more
exposed than pipelines, because injected text can reach a model holding tools.
L5
Record prompt tokens, completion tokens and cost at the time of the call, attributed per step as well as per
run. Report cost per 100 runs and the largest single cost driver.
L6
A feedback endpoint allowing the caller to mark a result satisfactory or not, with a reason, persisted and
aggregated. Score a small sample of live runs automatically against the evaluation metrics, charting quality
over time.

12. Cost
All software and data required are free. The corpus documents are public; sentence-transformers run locally
for embeddings at no cost, and a small model such as all-MiniLM-L6-v2 keeps memory use low; FAISS,
Chroma, LangGraph, CrewAI, LangChain, LlamaIndex, TruLens, FastAPI, Redis, Prometheus, Grafana,
OpenTelemetry, Jaeger and Locust are all free. For the model, use a provider's free tier. A local model via Ollama
is also possible but needs a considerably more powerful machine.
Embed locally. Embedding a corpus through a paid API is the only operation here with a real cost.
Agents multiply model calls — typically several per run, against one for a fixed pipeline. Free tiers also have
low rate limits, which is why load testing uses a stub (D6). This is the reason for the loop limits in A1, the caching
in D7 and the per-step cost tracking in L5. Set a spending limit on the account before starting, and place the
model behind an interface you control so the provider can be changed by configuration.
